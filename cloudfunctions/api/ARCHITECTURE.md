# API 架构与维护指南

## 当前实现

生产入口是 `index.js`，保留 RPC 分发、HTTP 支付通知分发、定时触发分发和统一错误处理。`index.refactored.js` 仅转发到同一个入口，不再维护第二套路由。

所有原有 25 个业务模块已经迁入 `handlers/`，包含真实业务实现。前端继续使用原有 module/action/data 协议，RPC 返回值保持 `{ ok: true, data }` 或 `{ ok: false, code, message }`。微信支付通知保持原生 SUCCESS/FAIL 响应。

目录职责：

- `config/database.js`：初始化云 SDK，创建数据库依赖。
- `config/constants.js`：从原入口迁出的实际业务常量。
- `handlers/index.js`：固定模块白名单、按需加载与实例内缓存。
- `handlers/*.js`：业务入口，每个工厂显式声明所需依赖。
- `services/context.js`：仅负责依赖装配，业务函数已全部迁出；按拓扑顺序构建服务，不做运行时动态依赖查找。
- `services/*.js`：53 个领域服务工厂，分别负责支付、结算、排班、订单、会员、消息、商城等业务。
- `services/paymentCallback.js`：验签、解密、处理支付通知；不属于 RPC action。
- `scheduled/index.js`：完整定时编排，包含取消、过期、提醒、超时处理、月度结算与补结算。
- `scheduled/cancelUnpaidOrders.js`、`scheduled/expireOrders.js`：订单定时处理。
- `utils/`：原有时间、响应、校验、加密和数据库辅助实现。

## 依赖规则

业务模块导出 `createHandler(context)`，返回 `(openid, action, data) => Promise`。不要在业务模块中初始化 SDK、导入生产 index.js 或读取其他模块的全局数据库实例。模块工厂可以被 Node 缓存，但持有数据库的 handler 实例由每个入口实例单独缓存，避免测试或多实例共享错误依赖。

新增模块时，在 `handlers/index.js` 注册固定加载器，并明确列出依赖。禁止用外部传入的模块名直接拼接 require 路径。共享函数应放入职责明确的服务中，context.js 不再承载业务实现。

领域服务采用 `createService({ dependencyA, dependencyB })`，返回具名业务函数。装配时依赖必须已初始化，禁止通过 getter、全局容器或互相 require 绕过循环依赖。架构测试会逐项检查装配所读取的依赖，并拒绝重复导出。每次 createContext 都产生独立服务实例，模块不得捕获全局数据库状态。

常用修改位置：

| 业务 | 服务文件 |

纯工具直接导出函数；涉及数据库或加密等依赖的工具通过工厂注入。保留 HOME_SECURITY_KEY、原有密文格式和错误格式，不能使用旧模板中的默认加密密钥或另一套响应结构。

## 支付与触发边界

paymentCallback 的实现已从 payment handler 移出。RPC 即使传入 `_isInternalHttpCallback: true` 也会拒绝。HTTP 分支及定时分支拒绝有 OPENID 的客户端上下文，支付通知仍必须经过验签和金额校验。

部署时必须在真实云环境验证 HTTP 触发器事件及 SDK 上下文。事件中的字段本身不是可信来源凭证；无 OPENID 也不是支付真实性凭证，验签不能关闭。定时入口仍需通过云端权限配置限制可调用者。

## 数据分页

getAllDocuments 已移除当前 SDK 不支持的 startAfter，使用 skip/limit，并以 _id 作为同时间记录的稳定排序字段。已用 250 条相同时间的数据验证无遗漏。

这不是快照读取，并发增删时仍可能变化；偏移很大时效率也会下降。财务看板已迁往数据库聚合，其他批处理应采用 SDK 支持的唯一键游标或固定数据快照。索引不能代替分页。

## 财务看板统计口径

admin.financeDashboard 调用 financeAggregation，不再读取六个集合的全部文档。金额、数量和状态分布在数据库分组计算；状态分组再次汇总成单条结果，避免分组结果本身超过 100 条被截断。仅最近日志返回 10 条原始记录，前端返回字段不变。mingo 仅作为根目录测试开发依赖，不进入云函数生产依赖。

- GMV 保留服务 orders 口径，补充 day_completed；不是服务与商城的合计成交额。
- 实收统计 payments 的 success 和历史 paid，排除 targetType 为 staff_deposit 的保证金；包含服务和商城支付。没有支付记录时返回零，不用 GMV 推算。历史保证金若缺失 targetType，需对账修复。
- 退款金额只统计 success 的 refundAmount；amount 是原交易总额，不能作为退款金额替代。处理中、失败记录保留在数量和状态分布中，但不计入已退款金额。
- 收益与提现保留各自记录创建周期口径，提现金额按 pending、approved、paid 分列。金额按分汇总；参与金额计算的缺失、字符串、负数、非有限数及超出安全整数范围的数据明确报错，不静默计零。历史金额字符串需要核验迁移。
- 日期为北京时间自然日，结束日期使用下一日零点的排他边界，包含最后一秒的毫秒。兼容 Date、带时区 ISO 字符串及无时区的北京时间字符串；按原字段优先级取第一个可解析日期。无有效日期的记录在有日期筛选时不计入。历史非标准日期及数字时间戳应先迁移为 Date。
- 付款优先 paidAt；退款仍按 createdAt/updatedAt 而非退款成功日统计，因此历史月份金额可能随着退款状态改变。不应把当前净收入/毛利公式当作权责发生制利润；尚未扣除商城成本、税费和其他经营费用。

跨集合聚合不是同一时刻的事务快照，统计期间发生支付和退款可能短暂不一致。历史日期归一化使用计算字段，不能保证命中日期索引；大规模数据下一步应统一原生 Date 和会计入账字段，并建立日汇总及对账机制。明细列表的分页、收益刷新批处理不在本轮修改范围内。

本地测试使用聚合执行库，日期解析适配器只模拟测试涉及的格式，不代表云端兼容性证明。已离线检查 wx-server-sdk 4.0.2 管道序列化；上线前必须在测试云环境验证 $type、dateFromString、时区、混合历史数据和查询耗时，并与微信账单对账。本轮未部署。

## 验证与发布

在仓库根目录执行 `npm test`。覆盖原业务回归，以及模块依赖、实例隔离、RPC 回调拒绝、客户端伪造触发器、分页和定时编排测试。支付相关用例通过 HTTP 入口检查验签拒绝、重复回调和金额不匹配，不再通过 RPC 模拟合法支付通知。

部署需上传整个 api 云函数目录并安装现有生产依赖，不能只上传 index.js。迁移工具使用的 AST 包不是生产依赖。上线前在测试环境验证真实支付、退款、提现、订阅通知和定时触发器。回滚时需将入口及其模块整体恢复到同一版本。

## 后续工作与边界

### 提现审批与纠纷结算

financialSettlement 统一提现审批、驳回、标记打款及纠纷冻结、结案的财务写入，旧 incidents 中的非事务扣减实现已移除。

- 审批和打款在事务内点读提现单及全部关联收益，检查员工、withdrawRequestId、withdrawing 状态、冻结标记和金额合计。提现单、收益、财务日志及管理员审计日志一起提交；相同目标状态重试不重复入账，冲突目标明确拒绝。
- 驳回只释放归属于当前提现单的收益；按 availableAt 恢复 pending 或 available。新提现申请也拒绝携带其他提现单或纠纷冻结标记的异常 available 记录。
- 纠纷冻结同时写入收益归属、纠纷 frozenEarningIds 和日志。重复冻结不会清空已有关联；其他纠纷不可覆盖冻结。提现中或已提现的收益明确拒绝冻结，不自动撤销提现或改动已打款资金。pending 提现需先驳回并确认成功，再重试冻结；approved/paid 必须先人工核实实际付款，不允许用纠纷接口强制解锁。
- 结案重新读取当前纠纷及收益，验证订单、员工和 frozenIncidentId；扣减、解冻、结案状态、处理结果、操作记录和订单时间线在同一事务提交。release/deduct 处理完成后不能再次更换决定；相同扣减请求幂等，keep_frozen 后仍可继续处理。
- 扣减按整数分累计，拒绝非有限、负数、不足分精度、超额金额。保留现有界面约定：deductAmount 为零或未填写表示全额扣减。关联收益超过 50 条、重复 ID、记录缺失或归属异常均明确报错，不进行部分操作或静默跳过。历史缺失 staffOpenid/frozenIncidentId 的冻结记录必须核对修复。
- 冻结候选通过事务回调内的普通查询发现，再进行事务点读与写入；保护的是查询发现的现有收益，不是未来收益。收益生成的唯一性、未生成收益的投诉预冻结、历史重复收益治理仍需专项处理。建议索引 staff_earnings (orderId, _id)。

已加入可交错快照及冲突重试模拟，覆盖审批争抢、重复打款、申请提现与冻结竞争、多纠纷竞争、释放与扣减竞争、归属校验及日志失败整体回滚。原接口权限及返回结构保留。本地测试不替代真实 CloudBase 并发联调，未部署。

markWithdrawPaid 仍是管理员对外部付款的本地记账确认，不发起真实转账，也不能提供银行/微信侧幂等保证。订阅消息在事务提交后发送，可靠重试和 outbox 尚未实现；不能以通知是否到达判断资金是否提交。

在模块化之后，已补充以下资金一致性处理：

- 提现申请由 withdrawals 服务处理，事务中重新校验收益所有人、状态和金额，并原子写入提现单、收益冻结和财务日志。clientRequestId 与员工身份共同生成固定单号；兼容历史提现单的请求号查询。事务失败不会遗留本次部分冻结。收益解冻使用 pending 条件更新，避免并发刷新将已提现收益重新解冻。
- 金额按分累计并校验有限正数。保留原有整笔收益选择方式，实际提现金额可能高于输入的目标金额；没有实现收益拆分。每次最多处理 50 笔收益，超出时明确拒绝并提示分批申请，不静默截断。
- 服务订单超时任务按 _id 分页；对微信支付单先查单，已支付则校验并补记付款，未支付则先关单。查单或关单失败时保留订单和券，记录错误并在之后的定时任务重试。取消、支付单关闭标记、对应锁定优惠券释放及时间线写入使用同一事务。
- 新建服务订单支付请求携带基于 createdAt 的 30 分钟 time_expire，超时后禁止新支付尝试。真实网关查询与关单在本地事务之外完成，可重复执行；远端已关闭、本地事务失败的情况由下次任务恢复。
- 接单预检查、实际接单、管理员派单共用按状态及 _id 分页的冲突查询，包含 day_completed 的未完成服务时段。后台派单逐个检查多日订单的服务时段，管理员手动恢复占用状态也进入相同并发约束。
- orderAssignment 的事务读取目标订单、宠托师用户及资料，并更新用户文档的 staffAssignmentRevision 和订单。不同订单竞争同一宠托师时，共享用户文档的写冲突会使事务重试并重新查询排班；两人竞争同一订单由订单文档的事务冲突保护。没有新增集合或进程内锁。
- CloudBase 事务使用点读，候选订单通过事务回调内的普通分页查询枚举，再对发现的冲突记录进行事务点读确认。所有新增占用时段的写入必须经过 orderAssignment 并触碰同一用户文档；禁止新增绕过服务的直接派单、重新激活或修改服务时间接口。事务内无消息通知等外部副作用。
- 已补充乐观并发模拟测试，覆盖共享员工事务冲突及重试、同单争抢、不重叠订单、100 条以后的冲突、多日排班、管理员恢复及失败回滚。修正了排班日历及日期例外判断的北京时间跨日偏移。服务开始/结束时间不完整的历史订单会拒绝派单，需先修复数据。

新增测试覆盖并发提现、同请求重复投递、事务回滚和重试、205 条订单清理、支付抢先成功、关单失败、券归属校验及支付截止时间。模拟事务验证本地原子提交/回滚，不等同于真实 CloudBase 锁冲突测试；上线前必须在测试环境验证事务和微信查单、关单返回。
